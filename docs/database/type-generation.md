## Future destination and use

Generate `shared/database/database.types.ts` from the approved **public** schema. This is a cross-boundary physical-schema artifact, not a handwritten domain model. Until generated, do not import it or create a placeholder. Frontend files `frontend/src/lib/supabase/browser.ts`, `server.ts`, and `proxy.ts` can then use a relative type-only import, e.g. `import type { Database } from "../../../../shared/database/database.types";`, with `createBrowserClient<Database>` and `createServerClient<Database>` as appropriate. Verify each relative path and compile after integration. Future backend code may import the same type; turn `shared` into a package or establish aliases only if the repository later needs them. Keep generated types distinct from Gemini extraction Zod contracts and provisional portfolio API write-validation schemas. Types do not enforce RLS or validate requests at runtime.

## Future read-only procedure

1. Obtain separate authorization after schema approval/deployment. Independently verify the `nexus-portfolio-dev` project reference in the trusted project inventory/dashboard, and independently verify the production reference from the same trusted source. Confirm both refer to the intended projects; never infer either from a linked project, environment default, or project display name. Stop if uncertain or identical. The helper compares the supplied references but **cannot independently authenticate their identity**; incorrect caller-supplied values can defeat its guard.
2. Use a preinstalled and verified Supabase CLI executable, version **3.1.0**, plus the repo's installed TypeScript dependency. Confirm `supabase --version` and `supabase gen types typescript --help`. Configure only an approved development-scoped credential through the CLI's supported secure authentication mechanism; do not put it in commands, files, or logs. The 3.1.0 help lists `database_read` and potentially broader permissions, including `database_write`, for remote operation. Security owners must review the exact credential permissions and execution path before use; this helper does not enforce database read-only privileges. Stop if a read-only authorized path cannot be established. Generating types is a schema metadata read; it is not a migration.
3. In PowerShell, supply the independently verified references and an absolute path to the CLI explicitly:

   ```powershell
   node scripts/generate-database-types.mjs --project-ref $DevRef --verified-dev-ref $DevRef --production-ref $ProdRef --cli $SupabaseExe
   ```

   The helper checks all references, refuses the supplied production reference, verifies CLI version, and runs exactly `supabase gen types typescript --remote=<verified-dev-ref> --schema public`. It never invokes bare `--remote`, a linked project, `--local`, or a database URL. Passing the same `$DevRef` twice is not independent verification; complete step 1 first. It captures output, checks the CLI exit status, expected declarations and TypeScript syntax, then replaces the destination using a same-directory temporary file. Failed generation or validation leaves an existing file intact. These checks do not prove the schema is correct or that successful output is semantically complete.

4. Inspect the new file and `git diff -- shared/database/database.types.ts`; compare all resulting tables, columns, enums, functions and relationships with the reviewed, deployed schema. Investigate unexpected differences before use. Run TypeScript and tests after supplying the generated `Database` to clients. Never hand-edit generated output. Commit the reviewed artifact only under a separately authorized task.
5. For drift detection, on a clean working tree and under the same authorization and verified target, regenerate using the same pinned CLI and schema scope; `git diff --exit-code -- shared/database/database.types.ts` detects tracked drift. Also check `git status --short -- shared/database/database.types.ts` for an untracked first generation. A clean diff is evidence only for the target and time inspected, not proof of RLS, production parity, or migration approval. Review and reconcile any drift before committing.

Run the offline helper tests with `node --test scripts/generate-database-types.test.mjs`. They use process doubles and temporary files; they do not connect to Supabase, exercise a real CLI generation, or verify hosted permissions.
