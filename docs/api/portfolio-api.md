# Portfolio API foundation

The ten route/method combinations are provisional, private contracts. There is no database-backed implementation. Successful authenticated, valid requests currently return 503 `{"error":{"code":"unavailable"}}`. No integration tests or Postman success screenshots are possible until the approved schema and policies are deployed and verified. Tests use scoped repository doubles only.

The existing architecture supports App Router route handlers and request-scoped Supabase SSR authentication. The proposed ERD and RLS matrix describe portfolios and child education/experiences, but neither physical names nor columns are approved. The prepared profiles migration is also not deployed or approved. API fields `title`, `institution`, and `organization` are provisional contract proposals, not assertions about deployed columns. Each create requires its one non-empty trimmed string, maximum 200 characters; PATCH requires at least one recognized field. Unknown keys (including owner IDs) are rejected. IDs are UUIDs; bodies are limited to 16 KiB. No DELETE is offered.

Responses use `{ "data": ... }` on success: 200 for reads and updates, 201 for creates; lists return arrays. Errors use `{ "error": { "code": "..." } }`: 400 invalid_request, 401 unauthenticated, 403 forbidden for an established denial, 404 not_found for absent or invisible records, 409 conflict, 503 unavailable, and 500 internal_error. Private responses are no-store. Route method exports define supported methods; framework-generated method errors are handled by Next.js.

After approval, build a request-scoped adapter using the same cookie-based client that verified `auth.getUser()`, never a privileged client. Bind identity from that verified client, never input; use reviewed mappings and generated types only after schema deployment. Scope child operations to the parent and return null for missing or RLS-invisible parents/records. Map explicit policy denials to forbidden only when established; avoid distinguishing other owners from missing records. Review database error mappings and grants. Test with two real non-anonymous users and real RLS in an explicitly authorized disposable environment, including cross-owner parent IDs, writes, policies and protected columns. Mock tests cannot prove RLS.

Postman requires a legitimate authenticated browser session/cookie for the same origin and running frontend, with no secrets saved in the collection. The collection documents future success contracts; current authenticated requests return 503. Do not submit fabricated success screenshots as task evidence.
